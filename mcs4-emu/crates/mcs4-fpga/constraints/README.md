# FPGA Constraint Files

## Provenance

Each `i<chip>_gates_ice40.pcf` and `i<chip>_gates_spartan7.xdc` constrains
the gate-level synthesis top for that chip, generated by
`scripts/gate_to_verilog_v0.py` from the extracted transistor-level
netlist at `docs/evidence/gates_v0/<chip>/` and written to
`docs/evidence/verilog_v0/<chip>/i<chip>_gates.v`. The port list in each
constraint file is copied verbatim from that generated module's header --
the module header is the single source of truth for what a constraint
file may name. Regenerate the gate-level Verilog (and re-check the port
list against it) with:

```
python3 scripts/gate_to_verilog_v0.py --generate-testbench
```

`mcs4-fpga/Makefile` selects `constraints/$(TOP)_ice40.pcf` and
`constraints/$(TOP)_spartan7.xdc` for `MODE=gate`, where `TOP =
i$(CHIP)_gates`. There is one file pair per chip (4001/4002/4003/4004);
none of them constrain a `mcs4_top`/system-level module, because no such
gate-level top exists in `docs/evidence/verilog_v0/`.

## Port <-> pin matrices

VDD/VSS are ordinary logic ports on these gate-level netlists (the
extraction is a flat transistor-level netlist with no separate power
plane), not the fabric's real supply rails. They are pinned out here to
fixed-level test pins as a structural placeholder; do not wire them to
the board's actual VCC/GND supply pins.

### 4003 (docs/evidence/verilog_v0/4003/i4003_gates.v)

| port | direction | iCE40 HX8K-CT256 | Spartan-7 csga324 |
|------|-----------|-------------------|--------------------|
| VDD  | in        | B1                 | M13                |
| VSS  | in        | B2                 | M14                |
| Q2   | in        | C1                 | N13                |
| Q5   | in        | C2                 | N14                |
| Q6   | in        | D1                 | P13                |
| Q4   | out       | D2                 | P14                |

The extracted netlist names these ports Q2/Q5/Q6/Q4 (net-derived from the
transistor extraction pass), not CLOCK/DATA/EN as the 4003 datasheet
pinout would suggest. No port carries a CLOCK/CLK name, so neither
constraint file declares a `create_clock`; all three inputs are treated
as asynchronous until the extraction is cross-checked against the
datasheet pin function to identify which net is the true clock.

| VDD    | in        | B1                 | M13                |

| CMRAM0 | out       | C2                 | N14                |
| D0_PAD | out       | D1                 | P13                |

CLK1 is a module *output* in this gate-level netlist (the extracted 4004
generates its own two-phase clock internally); there is no external clock
input port, so no `create_clock` is declared.

## Status

Every pin assignment above is a placeholder pending board bring-up: no
physical iCE40 HX8K-CT256 or Spartan-7 xc7s25csga324 board has been wired
to these nets. Update the pin numbers here once hardware validation
(mcs4-emu/CLAUDE.md Phase 5 pending item: FPGA hardware validation) picks
a specific board and confirms which physical pins route to which header.

Each `i<chip>_gates_ice40.pcf` ball name is confirmed against the real
CT256 package database via `nextpnr-ice40 --hx8k --package ct256`: every
port synthesizes (`yosys synth_ice40`) and places-and-routes
(`nextpnr-ice40 --pcf ... --asc ...`) to completion with 0 unresolved
pins. B1/B2/C1/C2/D1/D2/E2/F1 are valid CT256 balls; E1 is not a CT256
user-IO ball (nextpnr rejects it as "package does not have a pin named
'E1'"), which is why 4001's `D2_PAD` uses `F1` instead. The Spartan-7
`PACKAGE_PIN` names have not been run through Vivado (not installed in
this environment) and carry the same placeholder caveat as the rest of
this table.
